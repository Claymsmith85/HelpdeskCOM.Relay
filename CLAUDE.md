# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CoreSpecialty Mail → Helpdesk relay: Azure Functions v4 (Node 24, TypeScript, CommonJS output). It bridges email and Helpdesk.com in both directions using **Microsoft Graph + the native M365 shared mailboxes** (no SendGrid): inbound mail is delivered by Graph change notifications, outbound mail is sent via Graph `sendMail`, and attachments are stored in SharePoint via Graph. `README.md` has the deployment topology, the full env-var table, and the Graph notification/standup details.

## Architecture — the big picture

> For a structural quick-reference — the module import DAG, per-module fan-in/fan-out, and the
> runtime linkage map (Mermaid) — see [`docs/DEPENDENCY_MAP.md`](docs/DEPENDENCY_MAP.md).

Four functions form one round-trip loop, with two timer/queue safety-nets around them. How they avoid double-processing and hand state to each other is the crux of this codebase. A seventh function (`sync-teams`) is independent of the mail loop — it provisions Helpdesk agents/teams from AAD.

- **`src/functions/notify.ts`** (`notify`, HTTP) — Graph change-notification receiver. Answers the subscription validation handshake (echo `validationToken`), validates `clientState`, and enqueues `{ mailbox, messageId }` onto a Storage Queue. The `mailbox` is the configured SMTP address read from the notification URL's `?mailbox=` query param (set per-mailbox by `subscriptions.ts` via `notificationUrlForMailbox`), **not** the objectId GUID Graph puts in the notification `resource` — the worker can normalize an address but can't resolve that GUID without `User.Read.All` (the app reg only has `Mail.*`/`Sites.Selected`/`GroupMember.Read.All`). Falls back to the resource id for any subscription created before this change. Deliberately tiny so it acks within Graph's ~3 s window.
- **`src/functions/process-mail.ts`** (`process-mail`, Queue trigger) — the inbound worker. Each queue item is treated as "drain this mailbox": it lists the **whole inbox** (`listInboxMessageIds`, capped at `MAIL_DRAIN_BATCH_SIZE`) and runs the per-message pipeline (`processSingleMessage`) over every id, not just the notified one — so mail whose notification was dropped (e.g. during an app reboot) is still picked up by the next notification. Mail **received before `MAIL_IGNORE_BEFORE`** (default the go-live boundary `2026-06-19T22:00:00Z` = 6 PM ET; June is EDT/UTC-4) is ignored — left untouched in the inbox, never ticketed/auto-replied — so the oldest-first drain doesn't churn through the pre-go-live backlog; enforced both as a server-side `receivedDateTime ge` `$filter` on the listing (old mail is never fetched) and a per-message guard (covers the always-included triggering id; fails *open* on a missing/unparseable date). A queue item may carry only a `mailbox` (no `messageId`) — that's a **sweep** item (see `sweep-inbox`). On every drain it **also lists the `MAIL_REPROCESS_FOLDER`** (default `Reprocess`, created on demand via `ensureMailFolder`) and replays those messages through the same pipeline as if newly arrived (`processSingleMessage(..., reprocess=true)`) — an admin drops mail into that folder to re-run it. A reprocessed message **bypasses the `MAIL_IGNORE_BEFORE` cutoff** (no listing `$filter`, and the per-message guard is skipped) and **suppresses the customer auto-reply** (ticket-only, silent), but is otherwise identical — find-or-create, attachments, and the move to the processed folder. The Reprocess listing is best-effort and isolated so its failure can't regress the inbox drain. For each message it fetches the message + attachments from Graph, finds-or-creates a Helpdesk ticket, uploads attachments to SharePoint, sends the auto-reply (**reply-received only** — a **new** ticket is opened silently, with **no "ticket created" notice** to the requester from the relay or from Helpdesk) / oversize note / (error-only) debug mail, then **moves the message to a processed folder** for idempotency. A full listing page (inbox *or* Reprocess) re-enqueues a self-terminating continuation drain so big backlogs clear across several short invocations.
- **`src/functions/helpdesk.ts`** (`helpdesk`, HTTP) — Helpdesk `tickets.create` / `tickets.update` webhook. Emails the requester on agent replies via Graph `sendMail`.
- **`src/functions/renew-subscriptions.ts`** (`renew-subscriptions`, Timer) — creates/renews one Graph subscription per mailbox (message subscriptions expire after ~2.9 days). `runOnStartup` so a restart re-establishes them immediately; per-mailbox isolated so one bad mailbox can't starve the others (it still throws at the end if any failed).
- **`src/functions/sweep-inbox.ts`** (`sweep-inbox`, Timer) — safety-net. The drain is otherwise only triggered by a live notification, so if notification *delivery* breaks (lapsed subscription, Graph/WAF outage, restart past the TTL) mail strands in the inbox. This enqueues a mailbox-only drain item per mailbox every `MAIL_SWEEP_CRON` (default 15 min) and `runOnStartup`, so outstanding mail is always picked up regardless of delivery.
- **`src/functions/mail-poison.ts`** (`mail-poison`, Queue trigger on `<queue>-poison`) — logs dead-lettered drains at ERROR severity so a silent drop is alertable. Logs only; the sweep re-derives anything still in the inbox.
- **`src/functions/sync-teams.ts`** (`sync-teams`, Timer) — **independent of the mail loop.** Reconciles Helpdesk **agents/teams/roles** from AAD security groups (`TEAM_SYNC_CRON`, default hourly; **not** `runOnStartup`, because it can delete agents). Thin wrapper over `team-sync.ts`'s `runTeamSync` (logic/timer split mirrors `subscriptions.ts`/`renew-subscriptions.ts`). Helpdesk has no team-membership resource — a team is a set of agents and membership lives as a `teamIDs` array on each agent — so the sync PATCHes agents. The group→team/role mapping is **hardcoded per environment** in `team-mapping.ts` (`RULES_BY_ENV`, like `routing.ts`'s `TEAM_BY_INBOX`) — rules `{ group(AAD objectId), team?, role }` (`team` omitted = role-only group, e.g. Viewers). The active table is chosen by `rulesForEnvironment(process.env.RELAY_ENVIRONMENT)` (`Production`|`Development`, injected from the deploy matrix), defaulting to the **Development** table when unset/unknown so a misconfigured deploy can't run Production's destructive reconcile. Each member accumulates the union of roles + teams across their groups, inviting with the most-privileged role (`owner > normal > viewer`). Key invariants: **mapped-teams-only** (never touches an agent's non-mapped/manual teams; add/remove is strictly per-team), **decommission only when an agent ends in NO mapped group AND zero Helpdesk teams** (mapped+manual) — fully orphaned; `TEAM_SYNC_CLEANUP_ORPHANS` (default on) also reaps pre-existing zero-team/no-group agents, else only ones de-teamed this run; `TEAM_SYNC_PROTECTED_AGENTS` emails are never deleted (left fully untouched), and orphan cleanup is suppressed for the whole run if any group read fails. **Removal safety**: an empty/failed group read suppresses that team's removals; `TEAM_SYNC_MAX_REMOVALS` caps removals+orphan-deletes per run — over the cap all removals/deletes are skipped that run while adds still apply; `TEAM_SYNC_DRY_RUN` logs intended changes only. The reconciler `planTeamSync` is a **pure function** (heavily unit-tested); group reads + applies are per-item isolated and rethrown at the end. **Failure alerts, routed by category** (`alerts.ts` engine): a run's failures are split into two once-daily digests — `POST /agents` refused with `limitExceeded` (Helpdesk has no seats left — it exposes no quota endpoint, so this is only discoverable by trying) batches every blocked user into **one** `licensing` email to the Management team (`seat-alert.ts`, Production only); every **other** failure (non-seat invite rejections, update/delete failures, failed group reads) digests into one `it` email to the Development / IT Support team (`sync-failure-alert.ts`, both environments, keyed by failure signature so a new failure mode the same day still alerts). Both best-effort and non-absolving: the item failures still fail the run.

Cross-file invariants — breaking any one causes mail loops, duplicate messages, or broken threading:

1. **Echo suppression.** A customer email-in is fully handled by `process-mail.ts` (ticket create — a **new** ticket sends no customer notice; a reply to an **existing** ticket sends a reply-received ack). Helpdesk then fires a `tickets.create` webhook for that same event; `helpdesk.ts` must email the requester **only when the create's last event is agent-authored**, or it would echo the customer's own message back. It still patches `customFields.email` regardless.
2. **Requester-hash round-trip.** Both halves live in `requester-hash.ts`: `toInboundHashedEmail` stores the requester as `<local>=<domain>@<RELAY_HASH_DOMAIN>` (the single `@` becomes `=`; reversible and subdomain-safe) and `decodeRequesterEmail` reverses it (last `=` is the boundary, with a legacy `.`-form fallback, and passthrough for addresses not under the hash domain). This sink domain has no real mailbox, so Helpdesk's own notifications never reach the customer — the relay is the sole outbound path. Keep the value stable so existing tickets still decode. `RELAY_HASH_DOMAIN` is **required** (no built-in default — `hashDomain()` throws if it is unset).
3. **Subject threading.** `src/functions/subject.ts` (shared) embeds `[#<shortID>]` in outbound subjects; inbound matching (`findExistingTicket`) prefers that tag over a subject-substring match. `withTicketRef` strips existing tags before re-appending so they don't accumulate.
4. **Idempotency / at-least-once.** Graph can deliver duplicate notifications and the queue retries on a throw. Primary guard: `process-mail` moves the handled message to `MAIL_PROCESSED_FOLDER`; the move assigns a new message id, so a duplicate notification's original id **404s on `getMessage` and is skipped**. Because the side effects aren't transactional, anything that runs **after the ack is sent must be best-effort** (it must not throw — otherwise a retry would re-handle the now-existing ticket and send a *second* ack); e.g. the new-ticket attachment-link follow-up is wrapped. The move itself is best-effort but **not** silent: a 404 is the idempotent outcome (already moved); any other failure is logged at ERROR (it leaves the message in the inbox to be re-listed and re-acked). The remaining window — truly-concurrent drains of the *same* mailbox on *different* instances, where both clear `findExistingTicket` before either moves the message → duplicate ticket + duplicate ack — is closed by **`drain-lock.ts`**: each drain takes a per-mailbox Azure Storage **blob lease** before doing any work and releases it after, so same-mailbox drains can't overlap. (`host.json` `batchSize: 1` only removes *in-instance* concurrency; on the multi-instance Premium plan that alone is insufficient — this was a real prod duplication bug, June 2026.) The lock is keyed on the **canonicalized** mailbox (`routing.normalizeMailboxKey` → `<local>@corespecialty.com`, the UPN domain) so the two triggers collide on one lease: `notify` enqueues the per-mailbox address from its URL and `sweep-inbox` enqueues the `MAILBOX_ADDRESSES` entry — either may be on an **alias domain** (e.g. `…@corespecialtyins.com`) that Graph's `/users/{upn}` can't resolve, so an email is normalized **deterministically** (string-swap to the UPN domain, no Graph call) rather than via `resolveMailboxAddress`. A bare GUID (a pre-change notification) still falls back to `resolveMailboxAddress` + normalize; if that resolution fails the drain **aborts** (rather than locking on a divergent raw id) — but `sweep-inbox` still drains that mailbox under the correct key. (Real bug, June 2026: the alias-domain mailbox `ureferrals@corespecialtyins.com` stranded because canonicalization hard-resolved the raw id via Graph, which 404s on the alias and the GUID.) A contended drain **defers** (re-enqueues, no throw) rather than draining unlocked; a storage error **fails safe** (throws → queue retry → no unlocked drain). If a lease **renewal** fails mid-drain the lock is marked `lost` and the drain aborts at the next message boundary (queue retries under a fresh lease) so it never keeps running unlocked. Different mailboxes still drain in parallel (scale-out preserved). A per-message failure inside a drain is isolated (siblings still process) and rethrown at the end so the queue retries — a retry re-lists and reprocesses **only** the still-in-inbox failures.

Boundary / shared modules (no Function registration, so freely importable + unit-testable):
- **`graph-client.ts`** — shared app-only Graph token + axios client; `graphConfigFromEnv` reads `GRAPH_*`, falling back to legacy `SPO_*`.
- **`graph-mail.ts`** — `getMessage` / `listMessageAttachments` / `fetchAttachmentBytes`, `parseGraphMessage`, `sendMailViaGraph`, `ensureMailFolder`/`moveMessageToFolder`, oversize-note + debug builders.
- **`graph-directory.ts`** — `listGroupMemberUsers` (transitive AAD group **user** members via Graph, paginated); used only by the team sync. Needs `GroupMember.Read.All` (not the `Mail.*` scopes).
- **`sharepoint.ts`** — resolve site → drive by name → ensure folder (create-or-409-reuse) → content `PUT` (≤10 MiB) or chunked upload session; consumes `SharePointUploadItem`s with lazy `getBytes`.
- **`helpdesk-client.ts`** — Helpdesk REST client + ticket ops (`createTicket`/`updateTicketMessage`/`listTicketsByRequester`/`getTicketShortId`/`patchCustomFields`) + `findExistingTicket`, **plus agent/team ops** for the team sync (`listAgents`/`listTeams`/`inviteAgent`/`updateAgentTeams`/`deleteAgent`). Both `process-mail` and `helpdesk` use it (so `HELPDESK_BASE_URL`/auth live in one place).
- **`team-sync.ts`** — AAD→Helpdesk team-sync logic (no registration): `bestRole`, the pure `planTeamSync` reconciler, and `runTeamSync` orchestration. Consumed by `sync-teams.ts`.
- **`team-mapping.ts`** — hardcoded per-environment `RULES_BY_ENV` (AAD group objectId → Helpdesk team ID + role) + `rulesForEnvironment`; the single source of truth for the sync's mapping, keyed by `RELAY_ENVIRONMENT`. Also the alert routing: `AlertCategory` (`it` | `licensing`) and `ALERT_TEAMS_BY_ENV` / `alertTeamForEnvironment` — the Helpdesk team each alert category mails per environment (`licensing` → Mgmt. Team, **Production only**, `undefined` elsewhere ⇒ no mail; `it` → Development / IT Support, **both environments**). Kept here so every hardcoded team ID is PR-reviewed in one file.
- **`alerts.ts`** — the generic email-alert **engine** (consumed by the alert definitions, never called with hand-rolled throttling). `sendAlert({category, key, subject, body, graph, agents, environment})` routes by category via `ALERT_TEAMS_BY_ENV`, resolves recipients from the caller's already-fetched agent list (loop-guarded through `shouldSuppressRecipient`), throttles to one mail per (environment, key, Eastern day) via a create-once blob (`If-None-Match: *`, fail-closed on storage errors, claim released if every send fails), appends the environment footer, and sends from `ALERT_FROM_MAILBOX` (default the Escape mailbox). Kill switches `ALERT_ENABLED` + `ALERT_<CATEGORY>_ENABLED`, read per-invocation. **New alert = a definition module calling `sendAlert`; new category = extend `AlertCategory` + a row in `ALERT_TEAMS_BY_ENV`.**
- **`seat-alert.ts`** — the `licensing` alert definition: "Helpdesk is out of agent licenses" (consumed by `team-sync.ts`). `seatLimitFromError` recognizes `POST /agents`' `409 {"error":{"type":"limitExceeded",…,"details":{"lackingSeats":N}}}` — it keys on the error **`type`**, not the status, because a duplicate-email conflict is *also* a 409. Stable throttle key `seat-limit`.
- **`sync-failure-alert.ts`** — the `it` alert definition: a digest of a sync run's **non-seat** failures (invite 422s/5xx, update/delete failures, failed group reads; consumed by `team-sync.ts`). Its throttle key embeds the failure signature (sorted distinct `op`+`status`, e.g. `sync-failure-invite422`) so a persistent failure mails once daily but a new failure mode the same day still alerts.
- **`storage-client.ts`** — `buildStorageClient`: the axios + UAMI blob-storage REST client, shared by `drain-lock.ts` (leases) and `alerts.ts` (the daily-claim blobs). Extracted from `drain-lock.ts`; same `AzureWebJobsStorage` account and RBAC, so a new caller needs no new grant.
- **`requester-hash.ts`** — `hashDomain` + the encode/decode round-trip (invariant #2).
- **`routing.ts`** — `TEAM_BY_INBOX`, `normalizeInbox`, `routeTeam`, `shouldIgnoreSender` (inbound loop guard), `shouldSuppressRecipient` (outbound loop guard).
- **`logging.ts`** — `createStepLogger` / `createBufferedLogger` / `safeJson` / `formatAxiosError`.
- **`subscriptions.ts`** — create/renew Graph subscriptions. **`subject.ts`** — `[#shortID]` threading.
- **`drain-lock.ts`** — per-mailbox Azure Storage **blob lease** (REST via axios + the UAMI) that serializes same-mailbox drains across instances (invariant #4). `acquireDrainLock` returns a lock, `null` (contended → caller defers), or throws (storage error → caller fails safe); auto-renews while held, releases on success/throw, lease auto-expires on crash. Escape hatch: `DRAIN_LOCK_ENABLED=false`.

**`src/index.ts`** runs `app.setup(...)` and imports the seven function modules for side-effect registration.

Other behavioral invariants worth preserving:
- **Master feature toggles (`TICKETING_TOGGLE` / `USERMGMT_TOGGLE`), both default-OFF.** Two on/off switches (parsed by `env.ts`'s `envFlag`; `true`/`on`/`1`/`yes` = on, everything else incl. unset/empty = off — read **per-invocation** so they flip via an app setting with no redeploy). `TICKETING_TOGGLE` gates **all mail-flow interaction**: when off, `process-mail` returns at the top of the handler (before the drain lock / any Graph call) and the `helpdesk` webhook returns `200` immediately — **no ticket create/update and no outbound email**, and crucially the worker **never moves mail to the processed folder**, so mail sits untouched in the inbox and the whole OFF-window backlog is **caught up on the next drain** once re-enabled (`sweep-inbox`/notifications keep enqueuing drains meanwhile). `USERMGMT_TOGGLE` gates `sync-teams`: when off the timer no-ops (no agent invite/update/delete); the sync is a reconcile so a paused run loses nothing. **Because both default OFF, a freshly deployed environment is dark until the GitHub `vars.TICKETING_TOGGLE` / `vars.USERMGMT_TOGGLE` are set to `true`** (per environment). Subscription renewal and the inbox sweep are intentionally **not** gated — the "off" state only stops the actioning steps, keeping the plumbing warm for instant catch-up.
- **Debug email is error-only**, gated by `SEND_DEBUG_EMAIL === "true"` — only the `catch` path calls `sendDebugEmail`. It always sends **from the mailbox the message landed in** (the one being processed), which the app's Application Access Policy already licenses it to send as — there is no sender override.
- **Loop guard (both directions)**: inbound, `shouldIgnoreSender` drops mail *from* the hash domain / `helpdesk.com` / the `onmicrosoft.com` tenant. Outbound, `shouldSuppressRecipient` suppresses any send (ack in `process-mail`, agent reply in `helpdesk`) whose recipient is one of *our own* addresses — sending there would deposit mail into an inbox the relay drains, opening a new ticket that acks back, looping. It suppresses (1) anything `shouldIgnoreSender` would, (2) an exact `MAILBOX_ADDRESSES` entry (any domain), and (3) the **same drain mailbox under an alias company domain** — a recipient whose canonical mailbox key (`normalizeMailboxKey`, local part) matches a `MAILBOX_ADDRESSES` mailbox **and** whose domain is in-scope (`corespecialty.com` / `corespecialtyins.com`, overridable via `RELAY_IN_SCOPE_DOMAINS`); this catches the UPN-domain spelling of a mailbox enumerated on an alias domain (e.g. `escape@corespecialty.com` for a configured `escape@corespecialtyins.com`) without suppressing an external same-local-part address (`escape@gmail.com`). It deliberately does **not** blanket-block company domains — ordinary internal senders **do** receive auto-replies/agent replies. (A drain mailbox reachable only under a *different-local-part* proxy alias must be listed explicitly in `MAILBOX_ADDRESSES`.)
- **Attachment size limit is per-file** (`ATTACHMENT_MAX_BYTES`, default 100 MiB): each non-ignored file at/under it uploads; files over it are skipped (in-limit siblings still upload) and named in an agent `System note:`. Inline images, sub-20 KB images, and `signature`-named images are ignored (not uploaded, not counted). `planAttachments` runs on metadata only; bytes are fetched **one file at a time** (`fetchAttachmentBytes` → `/$value`, no base64) and uploaded via a single content `PUT` (≤10 MiB) or a **chunked upload session** (Graph caps fragments at 60 MiB). A per-file upload failure (e.g. a non-file attachment that 404s on `/$value`) is logged and skipped — siblings still upload. `host.json` tunes queue `batchSize` + `functionTimeout` for the larger transfers.

## Gotchas

- **Module-load side effects.** Importing a function module runs its registration (`app.http` / `app.storageQueue` / `app.timer`); `notify.ts` also calls `output.storageQueue(...)` at load. Tests that import these must mock the registry, e.g. `jest.mock("@azure/functions", () => ({ app: { http: jest.fn(), setup: jest.fn(), storageQueue: jest.fn(), timer: jest.fn() }, output: { storageQueue: jest.fn(() => ({})) } }))`.
- **Most helpers are module-private.** Only the handlers plus a curated set of pure helpers are `export`ed (for testing). Add an `export` rather than restructuring.
- **`ATTACHMENT_MAX_BYTES` is read once at module load** — set it via attachment sizes in tests, not `process.env` after import.
- **Required env at runtime**: `HELPDESK_PAT`, `RELAY_HASH_DOMAIN`, the Graph app-reg identity (`GRAPH_CLIENT_ID`/`GRAPH_TENANT_ID`, or legacy `SPO_*`) + `MANAGED_IDENTITY_CLIENT_ID` (the user-assigned MI that federates the app reg — auth is **secretless**, there is no client secret), `MAILBOX_ADDRESSES`, `GRAPH_NOTIFICATION_URL`, `GRAPH_SUBSCRIPTION_CLIENT_STATE`. The Graph app reg needs `Mail.ReadWrite` + `Mail.Send` + `Sites.Selected` + `GroupMember.Read.All` (the last for the `sync-teams` AAD-group → team sync), with an Exchange **Application Access Policy** scoping only the `Mail.*` roles to the helpdesk mailboxes (the Access Policy does not constrain the directory read). Non-secret settings come from `Deploy.yml` `vars.*`; secrets are Key Vault references.
- **WAF must allow-list `/api/notify`.** The external APIM is behind an App Gateway WAF (`APIM-External-WAFv2`, Prevention mode, `Microsoft_DefaultRuleSet` + `BotManagerRuleSet`). Its custom Allow rule (`HelpdeskEmailRelay`) bypasses the managed rules only for URIs containing `email`/`helpdesk` — **`notify` must be added too** (per environment), or Graph's JSON change-notification POSTs trip the managed rules (missing-User-Agent `920320` + UnknownBots `300100` + SQLi-false-positive `99031001` → anomaly block `949110`) and never reach `notify`. Empty-body validation handshakes pass the WAF, so the subscription **validates/renews but never delivers** — a silent failure (verified 2026-06: ~7 test mails, both inbox- and whole-mailbox subscriptions, zero delivery until the WAF rule was fixed). The relay code is fine — a notification POSTed straight at `/api/notify` processes normally.
- **`build/` is git-ignored**; CI rebuilds it, and the deploy artifact stages `build/` + `node_modules` + `host.json` + `package*.json`.
- **Drain lock storage + RBAC.** `drain-lock.ts` reuses the `AzureWebJobsStorage` account for its lease blobs: it reads `AzureWebJobsStorage__accountName` (or `__blobServiceUri`) for the endpoint and `AzureWebJobsStorage__clientId` (falling back to `MANAGED_IDENTITY_CLIENT_ID`) for the UAMI it authenticates as (scope `https://storage.azure.com/.default`). It creates a `drain-locks` container on first use, so the UAMI needs **Storage Blob Data Contributor** (container create + blob lease) — already satisfied by the identity-based `AzureWebJobsStorage` setup, which requires Blob Data Owner/Contributor. Tunables (all optional, read once at load): `DRAIN_LOCK_ENABLED`, `DRAIN_LOCK_CONTAINER`, `DRAIN_LOCK_LEASE_SECONDS` (15–60), `DRAIN_LOCK_RENEW_MS`, `DRAIN_LOCK_ACQUIRE_WAIT_MS`, `DRAIN_LOCK_ACQUIRE_POLL_MS`.
- **Reprocess replays per-message, so a moved conversation = one ticket per email.** The Reprocess drain replays **each message in the folder individually** (`processSingleMessage` per id). Dragging an Outlook **conversation** into `Reprocess` moves *every* email in that thread, so reprocessing it creates **as many tickets as there are emails in the conversation** — find-or-create does not collapse a moved thread into a single ticket. To reprocess a thread as one ticket, move a **single** message, not the conversation (in Outlook, expand the conversation and drag the one email, or turn off conversation grouping).

## Accessing logs (Application Insights)

> ⛔ **This working copy has no live connection.** Do **not** attempt `az monitor app-insights query`,
> `az functionapp …`, or any other live Azure/Helpdesk call from this environment — there is no
> network path or credential, so the calls only waste a turn. Diagnose from the source, the tests,
> and log excerpts the user pastes in. Everything below is reference material for someone working
> from a machine that *does* have access.

Runtime logs (the `createStepLogger` traces, host status, exceptions, request/dependency telemetry) live in **Application Insights**, queried with `az monitor app-insights query`. Two environment gotchas bite every time:

- **Zscaler cert split.** The data-plane endpoint (`api.applicationinsights.io`) is TLS-intercepted by Zscaler, so `az monitor app-insights query` needs `REQUESTS_CA_BUNDLE` pointing at the Zscaler root (`%USERPROFILE%\Zscaler Root.cer`, the same file as the npm `cafile` / `NODE_EXTRA_CA_CERTS`). But ARM calls (`az account`, `az resource list`, `az functionapp …`) **fail** if it's set — `unset` it for those. Empty-string counts as "set to an invalid path", so use `unset`, not `REQUESTS_CA_BUNDLE=`.
- **Output rendering.** Use `-o json` (table/tsv often render blank here) and parse it; aggregates aliased `last` error with `BadArgumentError` (reserved-ish) — name them something else.

## Testing

Jest + ts-jest. Tests live beside the source as `src/functions/*.test.ts` and compile through **`tsconfig.test.json`** (CommonJS) — separate from the app build (`tsconfig.json`, NodeNext), which **excludes `*.test.ts`**.

Conventions:
- HTTP/Graph boundaries are mocked with `axios-mock-adapter` on the relevant axios instance. For `process-mail`/`helpdesk` handler tests, `axios.create` is spied (Helpdesk instance) and/or `./graph-mail` / `./sharepoint` are mocked at the module boundary.
- `@azure/identity` `getToken` is mocked for the SharePoint Graph pipeline tests (`sharepoint.e2e.test.ts`).
- `jest.config.js` strips the `.js` extension that `index.ts` puts on its relative imports (`moduleNameMapper`).
