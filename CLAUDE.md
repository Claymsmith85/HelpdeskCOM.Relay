# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CoreSpecialty Mail → Helpdesk relay: Azure Functions v4 (Node 24, TypeScript, CommonJS output). It bridges email and Helpdesk.com in both directions using **Microsoft Graph + the native M365 shared mailboxes** (no SendGrid): inbound mail is delivered by Graph change notifications, outbound mail is sent via Graph `sendMail`, and attachments are stored in SharePoint via Graph. `README.md` has the deployment topology, the full env-var table, and the Graph notification/standup details.

## Architecture — the big picture

> For a structural quick-reference — the module import DAG, per-module fan-in/fan-out, and the
> runtime linkage map (Mermaid) — see [`docs/DEPENDENCY_MAP.md`](docs/DEPENDENCY_MAP.md).

Four functions form one round-trip loop, with two timer/queue safety-nets around them. How they avoid double-processing and hand state to each other is the crux of this codebase. Two further functions are independent of the mail loop: a seventh (`sync-teams`) provisions Helpdesk agents/teams from AAD, and an eighth (`archive-chats`) archives ended LiveChat conversations to SharePoint.

- **`src/functions/notify.ts`** (`notify`, HTTP) — Graph change-notification receiver. Answers the subscription validation handshake (echo `validationToken`), validates `clientState`, and enqueues `{ mailbox, messageId }` onto a Storage Queue. The `mailbox` is the configured SMTP address read from the notification URL's `?mailbox=` query param (set per-mailbox by `subscriptions.ts` via `notificationUrlForMailbox`), **not** the objectId GUID Graph puts in the notification `resource` — the worker can normalize an address but can't resolve that GUID without `User.Read.All` (the app reg only has `Mail.*`/`Sites.Selected`/`GroupMember.Read.All`). Falls back to the resource id for any subscription created before this change. Deliberately tiny so it acks within Graph's ~3 s window.
- **`src/functions/process-mail.ts`** (`process-mail`, Queue trigger) — the inbound worker. `MAILBOX_DRAIN` gates the handler before the drain lock or any Graph call; when enabled, each queue item means "drain this mailbox," listing the **whole inbox** (`listInboxMessageIds`, capped at `MAIL_DRAIN_BATCH_SIZE`) plus `MAIL_REPROCESS_FOLDER` and running `processSingleMessage` for each id. Mail received before `MAIL_IGNORE_BEFORE` stays untouched (server-side filter + per-message guard); Reprocess bypasses that cutoff and remains requester-silent. After sender/cutoff guards, `TICKET_CREATE` independently gates all inbound Helpdesk and attachment work: when off, the message is deliberately moved to processed without a ticket; when on, the worker finds/creates/appends, uploads attachments, adds oversize notes, and then moves the source for idempotency. Existing-ticket acknowledgements additionally require `SUBMITTER_REPLIES` and remain suppressed for Reprocess and relayed non-requester threads. `FOLLOWERS_NOTICES` enables tagged non-requester by-ref threading only inside the drain+ticket path. A full Inbox or Reprocess page re-enqueues a self-terminating continuation drain.
- **`src/functions/helpdesk.ts`** (`helpdesk`, HTTP) — Helpdesk `tickets.create` / `tickets.update` webhook. It is dark (immediate `200`) only when `SUBMITTER_REPLIES`, `AGENT_NOTICES`, and `FOLLOWERS_NOTICES` are all off. Otherwise it runs enabled notice audiences first and best-effort: the assigned agent gets public-message copies including their own Helpdesk-authored replies when `AGENT_NOTICES` is on (same-address relayed email is loop-suppressed); the existing follower / people-in-the-loop pass runs when `FOLLOWERS_NOTICES` is on. The create branch always patches `customFields.email` while the webhook is live; requester-facing agent-reply emails in create/update additionally require `SUBMITTER_REPLIES` and retain every email-source / author / privacy / system-note / missing-field gate.
- **`src/functions/renew-subscriptions.ts`** (`renew-subscriptions`, Timer) — creates/renews one Graph subscription per mailbox (message subscriptions expire after ~2.9 days). `runOnStartup` so a restart re-establishes them immediately; per-mailbox isolated so one bad mailbox can't starve the others (it still throws at the end if any failed).
- **`src/functions/sweep-inbox.ts`** (`sweep-inbox`, Timer) — safety-net. The drain is otherwise only triggered by a live notification, so if notification *delivery* breaks (lapsed subscription, Graph/WAF outage, restart past the TTL) mail strands in the inbox. This enqueues a mailbox-only drain item per mailbox every `MAIL_SWEEP_CRON` (default 15 min) and `runOnStartup`, so outstanding mail is always picked up regardless of delivery.
- **`src/functions/mail-poison.ts`** (`mail-poison`, Queue trigger on `<queue>-poison`) — logs dead-lettered drains at ERROR severity so a silent drop is alertable. Logs only; the sweep re-derives anything still in the inbox.
- **`src/functions/sync-teams.ts`** (`sync-teams`, Timer) — **independent of the mail loop.** Reconciles Helpdesk **agents/teams/roles** from AAD security groups (`TEAM_SYNC_CRON`, default hourly; **not** `runOnStartup`, because it can delete agents). Thin wrapper over `team-sync.ts`'s `runTeamSync` (logic/timer split mirrors `subscriptions.ts`/`renew-subscriptions.ts`). Helpdesk has no team-membership resource — a team is a set of agents and membership lives as a `teamIDs` array on each agent — so the sync PATCHes agents. The group→team/role mapping is **hardcoded per environment** in `team-mapping.ts` (`RULES_BY_ENV`, like `routing.ts`'s `TEAM_BY_INBOX`) — rules `{ group(AAD objectId), team?, role }` (`team` omitted = role-only group, e.g. Viewers). The active table is chosen by `rulesForEnvironment(process.env.RELAY_ENVIRONMENT)` (`Production`|`Development`, injected from the deploy matrix), defaulting to the **Development** table when unset/unknown so a misconfigured deploy can't run Production's destructive reconcile. Each member accumulates the union of roles + teams across their groups, inviting with the most-privileged role (`owner > normal > viewer`). Key invariants: **mapped-teams-only** (never touches an agent's non-mapped/manual teams; add/remove is strictly per-team), **decommission only when an agent ends in NO mapped group AND zero Helpdesk teams** (mapped+manual) — fully orphaned; `TEAM_SYNC_CLEANUP_ORPHANS` (default on) also reaps pre-existing zero-team/no-group agents, else only ones de-teamed this run; `TEAM_SYNC_PROTECTED_AGENTS` emails are never deleted (left fully untouched), and orphan cleanup is suppressed for the whole run if any group read fails. **Removal safety**: an empty/failed group read suppresses that team's removals; `TEAM_SYNC_MAX_REMOVALS` caps removals+orphan-deletes per run — over the cap all removals/deletes are skipped that run while adds still apply; `TEAM_SYNC_DRY_RUN` logs intended changes only. The reconciler `planTeamSync` is a **pure function** (heavily unit-tested); group reads + applies are per-item isolated and rethrown at the end. **Failure alerts, routed by category** (`alerts.ts` engine): a run's failures are split into two once-daily digests — `POST /agents` refused with `limitExceeded` (Helpdesk has no seats left — it exposes no quota endpoint, so this is only discoverable by trying) batches every blocked user into **one** `licensing` email to the Management team (`seat-alert.ts`, Production only); every **other** failure (non-seat invite rejections, update/delete failures, failed group reads) digests into one `it` email to the Development / IT Support team (`sync-failure-alert.ts`, both environments, keyed by failure signature so a new failure mode the same day still alerts). A run that **applied** changes additionally sends one `changes` digest of the successful invites / team moves / deletes (`sync-change-alert.ts` — IT team in both environments **plus** Mgmt. in Production; stable key `team-changes` ⇒ at most one mail per environment per Eastern day, later same-day changes are traces-only; team IDs resolved to names best-effort via `listTeams`, raw IDs on failure; successes only — failures belong to the other two alerts — so a dry run never alerts). All best-effort and non-absolving: the item failures still fail the run.
- **`src/functions/archive-chats.ts`** (`archive-chats`, Timer) — **independent of the mail loop.** Archives ended LiveChat conversations to a SharePoint library (`CHAT_ARCHIVE_CRON`, default every 15 min; **not** `runOnStartup`, because a restart loop would burn billed LiveChat calls and the lookback window loses nothing). Thin wrapper over `chat-archive.ts`'s `runChatArchive` (same logic/timer split as `team-sync.ts`/`sync-teams.ts`). It **polls** `POST /v3.6/agent/action/list_archives` rather than subscribing to the `chat_deactivated` webhook: a webhook needs a Developer Console app and a second WAF-exposed endpoint, and its payload is IDs-only — the same API call would be needed anyway. The API contract shapes the loop: results are **one per thread** (natural key `chat.id`+`thread.id`, so a resumed chat archives as several file pairs), there is **no `ended_at`** field or filter anywhere in the API ("ended" is `thread.active === false`, only readable off a thread that was already listed), `filters.from`/`to` bound thread **creation** time (hence a lookback measured in days — `CHAT_ARCHIVE_LOOKBACK_HOURS`, default 72 — so the window still contains a chat when it finally ends), and the first request carries the filters while **every follow-up page sends `{ page_id }` alone** (the server retains them and rejects a resend; a 200-page safety limit guards a server that always echoes a next id). The window is **stateless** — there is deliberately no watermark to corrupt, misread at startup, or hand-fix after an incident: each run re-lists `[now − lookback, now]` and per-thread create-once claim blobs (`chat-archive-<chatId>_<threadId>` in `CHAT_ARCHIVE_CONTAINER`, default `relay-state`) decide what is actually new, so a run that is skipped, fails, or is switched off needs no repair. **The claim is written AFTER a successful upload — deliberately inverted from `alerts.ts`**, which claims *first* because sending email is not idempotent; here the side effect is an idempotent `replace` upload on a host-singleton timer, so the claim is cross-*run* memory rather than race arbitration, and claiming first would invent a permanent-loss path (claim survives, process dies before the upload, that transcript is never archived by any later run). So a claim-write failure is a WARN, not an item failure, while an *unreadable* claim (storage error) **is** an item failure — never archive blind. Because the claim is what makes the steady state cheap, the two ways a chat ends up **archived but unclaimed** are counted (`claimFailed`, `archivedUnconfirmed`) and raised at ERROR by `archive-chats.ts` **without failing the run** (the `sync-teams.ts` precedent) — otherwise a silently broken claim would re-upload the whole window every 15 minutes while every run reported success. `archivedUnconfirmed` covers the second one: only `thread.active === false` **proves** a conversation ended, so a thread whose `active` is absent or non-boolean is archived (matching the backlog script, which exports whatever was listed) but deliberately **left unclaimed**, letting the idempotent `replace` upload overwrite it once it really has ended — skipping instead would make the feature silently archive nothing if the field ever disappeared, and claiming would freeze a half-finished transcript in the library forever. Each ended thread writes **two files** into a `Year/Month/Day` folder keyed on the chat's start (`thread.created_at`) in `CHAT_ARCHIVE_TIME_ZONE` (default Eastern, so the day boundary is the business day, not UTC): `<Customer> - <chatId>_<threadId>.json` (a **fidelity** contract — the raw payload, fields this relay knows nothing about included) and `.txt` (the backlog script's transcript **layout** — CRLF, UTF-8 no BOM, agent-only events included and labeled; see `chat-transcript.ts` for the one line-type that cannot match). Per-chat isolated and rethrown at the end (the team-sync convention); nothing has to be repaired before the retry, because the next tick re-lists the same window.

Cross-file invariants — breaking any one causes mail loops, duplicate messages, or broken threading:

1. **Echo suppression.** A customer email-in is handled by `process-mail.ts` (new ticket: always silent; existing-ticket reply: ack only with `SUBMITTER_REPLIES`). Helpdesk then fires a `tickets.create` webhook for the same event; the requester path must email **only when the create's last event is agent-authored**, or it echoes the customer message back. It still patches `customFields.email` whenever the webhook is live. The **follower/cc audience** keeps its existing echo controls: never mail the requester, event author (ID, payload email, or resolved agent email), or `[Relayed from …]` sender; forged markers are neutralized at ingest. The **assigned-agent audience deliberately does not exclude an agent author** — the agent receives copies of their own Helpdesk-authored public replies. It does exclude the same assigned address when a generic client event carries `[Relayed from that address]`, preventing an out-of-office reply from ping-ponging through the inbound thread. If the assigned agent also equals the requester, the independent submitter and agent paths may both send; accepted. Every outbound recipient still passes `shouldSuppressRecipient`.
2. **Real requester + Helpdesk notifications disabled.** The ticket requester is the customer's real email address, stored unaltered (`createTicket` `requesterEmail: parsed.fromAddress`) and mirrored into `customFields.email` — the field the `helpdesk` webhook's update branch sends agent replies to (the create branch patches it for UI-created tickets). This is only safe because **Helpdesk's own requester notifications are disabled in Helpdesk's admin settings** — the relay is the sole outbound path (existing-ticket ack from `process-mail`, agent replies from the webhook). **Re-enabling Helpdesk's requester notifications double-emails the customer on every event** — there is no code-level guard against it. Transition note: tickets created before the 2026-08 cutover (and stale Helpdesk **contacts**) carry the old hashed form `<local>=<domain>@<old sink domain>`; replies to those tickets miss the requester lookup and open a new ticket, and an agent reply to a stale hashed contact bounces silently at the dead sink until the ticket's `email` custom field is hand-corrected.
3. **Subject threading.** `src/functions/subject.ts` embeds `[#<shortID>]` in outbound subjects; inbound matching prefers that tag over a subject-substring match, and `withTicketRef` strips old tags before re-appending. Tagged non-requester threading requires **all three** of `MAILBOX_DRAIN`, `TICKET_CREATE`, and `FOLLOWERS_NOTICES`; with ticket creation off, no by-ref lookup runs. An enabled tagged reply from a follower/person-in-the-loop (invisible to requester-scoped `listTicketsByRequester`) resolves via `findTicketByShortId` (`GET /tickets?shortID=…`, client-side verified) and appends with the relayed-from marker. The tag is authoritative over a sender-owned subject fallback but never grants access: the sender must be the requester, cc, or follower agent. Outsiders fall through to a silent new ticket. Relayed non-requester threads send no ack (auto-responder loop guard). Definitive 4xx falls through; 5xx or transient 408/429 rethrows before any side effect so a retry cannot fork the conversation.
4. **Idempotency / at-least-once.** Graph can deliver duplicate notifications and the queue retries on a throw. Primary guard: `process-mail` moves the handled message to `MAIL_PROCESSED_FOLDER`; the move assigns a new message id, so a duplicate notification's original id **404s on `getMessage` and is skipped**. Because the side effects aren't transactional, anything that runs **after the ack is sent must be best-effort** (it must not throw — otherwise a retry would re-handle the now-existing ticket and send a *second* ack); e.g. the new-ticket attachment-link follow-up is wrapped. The move itself is best-effort but **not** silent: a 404 is the idempotent outcome (already moved); any other failure is logged at ERROR (it leaves the message in the inbox to be re-listed and re-acked). The remaining window — truly-concurrent drains of the *same* mailbox on *different* instances, where both clear `findExistingTicket` before either moves the message → duplicate ticket + duplicate ack — is closed by **`drain-lock.ts`**: each drain takes a per-mailbox Azure Storage **blob lease** before doing any work and releases it after, so same-mailbox drains can't overlap. (`host.json` `batchSize: 1` only removes *in-instance* concurrency; on the multi-instance Premium plan that alone is insufficient — this was a real prod duplication bug, June 2026.) The lock is keyed on the **canonicalized** mailbox (`routing.normalizeMailboxKey` → `<local>@corespecialty.com`, the UPN domain) so the two triggers collide on one lease: `notify` enqueues the per-mailbox address from its URL and `sweep-inbox` enqueues the `MAILBOX_ADDRESSES` entry — either may be on an **alias domain** (e.g. `…@corespecialtyins.com`) that Graph's `/users/{upn}` can't resolve, so an email is normalized **deterministically** (string-swap to the UPN domain, no Graph call) rather than via `resolveMailboxAddress`. A bare GUID (a pre-change notification) still falls back to `resolveMailboxAddress` + normalize; if that resolution fails the drain **aborts** (rather than locking on a divergent raw id) — but `sweep-inbox` still drains that mailbox under the correct key. (Real bug, June 2026: the alias-domain mailbox `ureferrals@corespecialtyins.com` stranded because canonicalization hard-resolved the raw id via Graph, which 404s on the alias and the GUID.) A contended drain **defers** (re-enqueues, no throw) rather than draining unlocked; a storage error **fails safe** (throws → queue retry → no unlocked drain). If a lease **renewal** fails mid-drain the lock is marked `lost` and the drain aborts at the next message boundary (queue retries under a fresh lease) so it never keeps running unlocked. Different mailboxes still drain in parallel (scale-out preserved). A per-message failure inside a drain is isolated (siblings still process) and rethrown at the end so the queue retries — a retry re-lists and reprocesses **only** the still-in-inbox failures. Known amplification with `FOLLOWERS_NOTICES` on: an at-least-once re-append (ticket updated but the move-to-processed failed) re-fires the `tickets.update` webhook, so the duplicate isn't just one re-ack anymore — the notice pass re-fans to every follower/cc. Accepted (same failure window as the documented re-ack case; the failed move is already ERROR-logged); the escape hatch if it bites is a per-`(ticketId, eventID)` create-once claim via `storage-client.ts`.

Boundary / shared modules (no Function registration, so freely importable + unit-testable):
- **`graph-client.ts`** — shared app-only Graph token + axios client; `graphConfigFromEnv` reads `GRAPH_*`, falling back to legacy `SPO_*`.
- **`graph-mail.ts`** — `getMessage` / `listMessageAttachments` / `fetchAttachmentBytes`, `parseGraphMessage`, `sendMailViaGraph`, `ensureMailFolder`/`moveMessageToFolder`, oversize-note + debug builders.
- **`graph-directory.ts`** — `listGroupMemberUsers` (transitive AAD group **user** members via Graph, paginated); used only by the team sync. Needs `GroupMember.Read.All` (not the `Mail.*` scopes).
- **`sharepoint.ts`** — resolve site → drive by name → ensure folder (create-or-409-reuse) → content `PUT` (≤10 MiB) or chunked upload session; consumes `SharePointUploadItem`s with lazy `getBytes`. `ensureFolderPath` generalizes the create-or-409-reuse idiom to a **multi-segment** path (the chat archive's `Year/Month/Day` tree); `uploadFileToDriveFolder` takes an optional `conflictBehavior` (default `rename`, so the attachment callers are unchanged — the archiver passes `replace`).
- **`helpdesk-client.ts`** — Helpdesk REST client + ticket ops (`createTicket`/`updateTicketMessage`/`listTicketsByRequester`/`getTicketShortId`/`findTicketByShortId`/`patchCustomFields`) + `findExistingTicket`, **plus agent/team ops** for the team sync (`listAgents`/`listTeams`/`inviteAgent`/`updateAgentTeams`/`deleteAgent`). Both `process-mail` and `helpdesk` use it (so `HELPDESK_BASE_URL`/auth live in one place).
- **`ticket-notices.ts`** — notice audiences (no registration; consumed by `helpdesk.ts`). `sendTicketNotices` takes explicit `{followers, agent}` flags so it stays env-independent, classifies the last event once, shares one lazily memoized `listAgents` call across follower extraction and assignment resolution, and never throws. The follower/cc path preserves its visibility ladder and author/requester/relayed-sender exclusions. The assigned-agent path accepts public messages only, includes an agent author, suppresses a same-address relayed marker sender, and wins cross-audience dedupe when the agent is also a follower/cc. Every send is loop-guarded and per-recipient isolated. `isSystemNoteText` remains shared with the requester gate.
- **`team-sync.ts`** — AAD→Helpdesk team-sync logic (no registration): `bestRole`, the pure `planTeamSync` reconciler, and `runTeamSync` orchestration. Consumed by `sync-teams.ts`.
- **`team-mapping.ts`** — hardcoded per-environment `RULES_BY_ENV` (AAD group objectId → Helpdesk team ID + role) + `rulesForEnvironment`; the single source of truth for the sync's mapping, keyed by `RELAY_ENVIRONMENT`. Also the alert routing: `AlertCategory` (`it` | `licensing` | `changes`) and `ALERT_TEAMS_BY_ENV` / `alertTeamsForEnvironment` — the Helpdesk team(s) each alert category mails per environment; a row may map **one team or a list** (recipients are the union). `licensing` → Mgmt. Team, **Production only**, `undefined` elsewhere ⇒ no mail; `it` → Development / IT Support, **both environments**; `changes` → IT in both environments plus Mgmt. in Production. Kept here so every hardcoded team ID is PR-reviewed in one file.
- **`alerts.ts`** — the generic email-alert **engine** (consumed by the alert definitions, never called with hand-rolled throttling). `sendAlert({category, key, subject, body, graph, agents, environment})` routes by category via `ALERT_TEAMS_BY_ENV`, resolves recipients from the caller's already-fetched agent list (loop-guarded through `shouldSuppressRecipient`), throttles to one mail per (environment, key, Eastern day) via a create-once blob (`If-None-Match: *`, fail-closed on storage errors, claim released if every send fails), appends the environment footer, and sends from `ALERT_FROM_MAILBOX` (default the Escape mailbox). Kill switches `ALERT_ENABLED` + `ALERT_<CATEGORY>_ENABLED`, read per-invocation. **New alert = a definition module calling `sendAlert`; new category = extend `AlertCategory` + a row (one team ID or a list) in `ALERT_TEAMS_BY_ENV`.**
- **`seat-alert.ts`** — the `licensing` alert definition: "Helpdesk is out of agent licenses" (consumed by `team-sync.ts`). `seatLimitFromError` recognizes `POST /agents`' `409 {"error":{"type":"limitExceeded",…,"details":{"lackingSeats":N}}}` — it keys on the error **`type`**, not the status, because a duplicate-email conflict is *also* a 409. Stable throttle key `seat-limit`.
- **`sync-failure-alert.ts`** — the `it` alert definition: a digest of a sync run's **non-seat** failures (invite 422s/5xx, update/delete failures, failed group reads; consumed by `team-sync.ts`). Its throttle key embeds the failure signature (sorted distinct `op`+`status`, e.g. `sync-failure-invite422`) so a persistent failure mails once daily but a new failure mode the same day still alerts.
- **`sync-change-alert.ts`** — the `changes` alert definition: a digest of the agent/team changes a sync run **successfully applied** (invites, team membership updates, deletes; consumed by `team-sync.ts`). Successes only — failed items are the `it`/`licensing` alerts' territory — and a dry run applies nothing, so it never alerts. Stable throttle key `team-changes` (the `seat-alert.ts` convention, deliberately not the failure-signature convention): at most one mail per environment per Eastern day; later same-day changes are visible only in the sync-teams traces. Takes an optional `teamNames` ID→name map for the body (the caller resolves it best-effort via `listTeams`; missing entries render as raw IDs).
- **`livechat-client.ts`** — the LiveChat (Text) **Agent Chat API v3.6** boundary (the `helpdesk-client.ts` shape): base URL, `Basic` credential, the shared retry interceptor, and the one operation the archiver needs (`listArchivesPage`); the paging loop and every archiving decision live in `chat-archive.ts`. `resolveLiveChatBasicToken` is read **per-invocation** (a missing credential throws at the point of use, not at import) and mirrors the backlog script's resolution — `LIVECHAT_BASIC_TOKEN` (the Developer Console's pre-encoded value; a copied `Basic ` prefix is stripped) then the `LIVECHAT_ACCOUNT_ID` + `LIVECHAT_PAT` pair — so **one Key Vault secret serves both**. The response types are deliberately loose (index signatures everywhere) because the archived `.json` must round-trip fields added after this was written.
- **`chat-transcript.ts`** — **pure** rendering + naming for one chat (no env reads, no I/O, `import type` only, so no runtime coupling to the API client). `transcriptText` is a one-to-one port of `scripts/Export-LiveChatTranscripts.ps1`'s `ConvertTo-TranscriptText`, reproducing PowerShell semantics that were **verified against pwsh, not inferred**: `True`/`False` capitalization, hardcoded CRLF, `IsNullOrWhiteSpace`-vs-truthiness per call site, case-**insensitive** `-eq`/`switch`/hashtable comparisons, and the pipeline's one-element-array unwrap (`answers: [{…}]` renders bare, not as a list — the common single-select prechat field). **One line-type cannot match and never will**: PowerShell's JSON reader turns ISO-8601 strings into `[DateTime]`, so the script renders `07/28/2026 13:05:11` (culture-dependent, sub-second digits and the `Z` lost) where this port echoes the API's `2026-07-28T13:05:11.123456Z`. The port is the faithful side; timestamp lines differ, every other line is identical. `chatJsonText` is the fidelity half (and strictly better than the script's, which re-serializes the mangled `DateTime`s). `customerDisplayName` (first `type === "customer"` user: name → email → `Unknown visitor`), `archiveBaseName` (`<customer capped at 100> - <chatId>_<threadId>`, through `sanitizeSharePointName`), `archiveFolderSegments` (zone-local `["2026","07","28"]`; **throws** on a missing/unparseable `created_at` → the caller isolates that chat).
- **`chat-archive.ts`** — the archiver's logic/orchestration (the `team-sync.ts` analog, consumed by `archive-chats.ts`): `chatArchiveOptionsFromEnv`, `toApiTimestamp` (list_archives wants **microsecond** RFC3339, so `Date`'s three digits are widened to six), `chatClaimBlobName`, and `runChatArchive` — pagination, the skip ladder (`thread.active` → already-seen-this-run → already-claimed), a lazily-resolved site/drive plus a per-day folder cache (so the steady-state "everything is already claimed" run costs **zero** Graph calls), the two `replace` uploads, then the claim. Both caches memoize the **promise**, not the resolved value, so a *rejection* is cached too — site/drive resolution is a run-level fact reached from inside the per-chat `try`, and re-attempting it per chat would fire hundreds of retried Graph GETs at the app registration the mail loop shares, burning the host timeout before the run could report anything. `chatClaimBlobName` deliberately does **not** fold case and reserves `_` as the separator (unlike `alerts.ts`'s version of the same transform, whose key space is hardcoded): these ids are opaque and external, blob names are case-sensitive, and a collision resolves as `blobExists → true`, i.e. silent permanent loss of the second thread.
- **`storage-client.ts`** — `buildStorageClient`: the axios + UAMI blob-storage REST client, shared by `drain-lock.ts` (leases), `alerts.ts` (the daily-claim blobs) and `chat-archive.ts` (per-thread archive claims). Extracted from `drain-lock.ts`; same `AzureWebJobsStorage` account and RBAC, so a new caller needs no new grant. Also owns the **create-once claim** idiom itself — `claimCreateOnceBlob` (PUT `If-None-Match: *`, `false` when it already exists), `releaseClaimBlob`, `blobExists` — lifted out of `alerts.ts` once a second caller needed it, so the two claim users can't drift apart.
- **`routing.ts`** — `TEAM_BY_INBOX`, `normalizeInbox`, `routeTeam`, `shouldIgnoreSender` (inbound loop guard), `shouldSuppressRecipient` (outbound loop guard).
- **`logging.ts`** — `createStepLogger` / `createBufferedLogger` / `safeJson` / `formatAxiosError`.
- **`subscriptions.ts`** — create/renew Graph subscriptions. **`subject.ts`** — `[#shortID]` threading.
- **`drain-lock.ts`** — per-mailbox Azure Storage **blob lease** (REST via axios + the UAMI) that serializes same-mailbox drains across instances (invariant #4). `acquireDrainLock` returns a lock, `null` (contended → caller defers), or throws (storage error → caller fails safe); auto-renews while held, releases on success/throw, lease auto-expires on crash. Escape hatch: `DRAIN_LOCK_ENABLED=false`.

**`src/index.ts`** runs `app.setup(...)` and imports the eight function modules for side-effect registration.

Other behavioral invariants worth preserving:
- **Feature toggles are default-OFF and read per invocation.** `env.ts` parses `true`/`on`/`1`/`yes` as ON; unset/empty/anything else is OFF, so app settings flip behavior without redeploy. The five independent mail switches allow all 32 combinations: `MAILBOX_DRAIN` gates the inbound handler before the lock/Graph and leaves mail untouched when off; `TICKET_CREATE` gates all inbound Helpdesk/attachment work while an enabled drain still moves mail when off; `SUBMITTER_REPLIES` gates existing-ticket acks and webhook requester emails; `AGENT_NOTICES` gates assigned-agent public-message copies including own Helpdesk-authored replies; `FOLLOWERS_NOTICES` gates follower/cc webhook notices plus tagged non-requester threading (the latter also requires drain+create). The webhook is dark only when all three webhook flags are off; a live create webhook patches `customFields.email` regardless of submitter email state. **Dev and prod share one Helpdesk account, so each webhook-driven toggle (`SUBMITTER_REPLIES`, `AGENT_NOTICES`, `FOLLOWERS_NOTICES`) must be ON in at most one environment or recipients are double-emailed.** `USERMGMT_TOGGLE` still gates `sync-teams`: when off the timer no-ops (no agent invite/update/delete); the sync is a reconcile so a paused run loses nothing. `CHAT_ARCHIVE_TOGGLE` still gates `archive-chats` before the LiveChat client is built; its stateless window catches up an off period within `CHAT_ARCHIVE_LOOKBACK_HOURS`. Subscription renewal and inbox sweep remain ungated. `Deploy.yml` maps the toggles from `vars.*`, but this repo currently has no GitHub environment variables configured; live settings are portal-managed, so re-verify all five after every deploy.
- **Debug email is error-only**, gated by `SEND_DEBUG_EMAIL === "true"` — only the `catch` path calls `sendDebugEmail`. It always sends **from the mailbox the message landed in** (the one being processed), which the app's Application Access Policy already licenses it to send as — there is no sender override.
- **Loop guard (both directions)**: inbound, `shouldIgnoreSender` drops mail *from* `helpdesk.com` / the `onmicrosoft.com` tenant and bounce senders (`postmaster`/`mailer-daemon` exact local part). Outbound, **every** ack, requester reply, follower/cc notice, and assigned-agent notice passes `shouldSuppressRecipient`; it blocks ignored-sender domains, exact `MAILBOX_ADDRESSES`, and the same drain mailbox under an in-scope alias company domain while allowing ordinary internal recipients.
- **Attachment size limit is per-file** (`ATTACHMENT_MAX_BYTES`, default 100 MiB): each non-ignored file at/under it uploads; files over it are skipped (in-limit siblings still upload) and named in an agent `System note:`. Inline images, sub-20 KB images, and `signature`-named images are ignored (not uploaded, not counted). `planAttachments` runs on metadata only; bytes are fetched **one file at a time** (`fetchAttachmentBytes` → `/$value`, no base64) and uploaded via a single content `PUT` (≤10 MiB) or a **chunked upload session** (Graph caps fragments at 60 MiB). A per-file upload failure (e.g. a non-file attachment that 404s on `/$value`) is logged and skipped — siblings still upload. `host.json` tunes queue `batchSize` + `functionTimeout` for the larger transfers.

## Gotchas

- **Module-load side effects.** Importing a function module runs its registration (`app.http` / `app.storageQueue` / `app.timer`); `notify.ts` also calls `output.storageQueue(...)` at load. Tests that import these must mock the registry, e.g. `jest.mock("@azure/functions", () => ({ app: { http: jest.fn(), setup: jest.fn(), storageQueue: jest.fn(), timer: jest.fn() }, output: { storageQueue: jest.fn(() => ({})) } }))`.
- **Most helpers are module-private.** Only the handlers plus a curated set of pure helpers are `export`ed (for testing). Add an `export` rather than restructuring.
- **`ATTACHMENT_MAX_BYTES` is read once at module load** — set it via attachment sizes in tests, not `process.env` after import.
- **Required env at runtime**: `HELPDESK_PAT`, the Graph app-reg identity (`GRAPH_CLIENT_ID`/`GRAPH_TENANT_ID`, or legacy `SPO_*`) + `MANAGED_IDENTITY_CLIENT_ID` (the user-assigned MI that federates the app reg — auth is **secretless**, there is no client secret), `MAILBOX_ADDRESSES`, `GRAPH_NOTIFICATION_URL`, `GRAPH_SUBSCRIPTION_CLIENT_STATE`. The Graph app reg needs `Mail.ReadWrite` + `Mail.Send` + `Sites.Selected` + `GroupMember.Read.All` (the last for the `sync-teams` AAD-group → team sync), with an Exchange **Application Access Policy** scoping only the `Mail.*` roles to the helpdesk mailboxes (the Access Policy does not constrain the directory read). Non-secret settings come from `Deploy.yml` `vars.*`; secrets are Key Vault references. **Additionally required once `CHAT_ARCHIVE_TOGGLE` is on**: `CHAT_ARCHIVE_LIBRARY_NAME` plus a LiveChat credential (`LIVECHAT_BASIC_TOKEN`, or the `LIVECHAT_ACCOUNT_ID` + `LIVECHAT_PAT` pair) — but **no new Graph permission**, since the archive library sits on the already-granted `Sites.Selected` site, and **no new storage RBAC**, since its claim blobs reuse the `AzureWebJobsStorage` account + UAMI.
- **WAF must allow-list `/api/notify`.** The external APIM is behind an App Gateway WAF (`APIM-External-WAFv2`, Prevention mode, `Microsoft_DefaultRuleSet` + `BotManagerRuleSet`). Its custom Allow rule (`HelpdeskEmailRelay`) bypasses the managed rules only for URIs containing `email`/`helpdesk` — **`notify` must be added too** (per environment), or Graph's JSON change-notification POSTs trip the managed rules (missing-User-Agent `920320` + UnknownBots `300100` + SQLi-false-positive `99031001` → anomaly block `949110`) and never reach `notify`. Empty-body validation handshakes pass the WAF, so the subscription **validates/renews but never delivers** — a silent failure (verified 2026-06: ~7 test mails, both inbox- and whole-mailbox subscriptions, zero delivery until the WAF rule was fixed). The relay code is fine — a notification POSTed straight at `/api/notify` processes normally.
- **`build/` is git-ignored**; CI rebuilds it, and the deploy artifact stages `build/` + `node_modules` + `host.json` + `package*.json`.
- **Drain lock storage + RBAC.** `drain-lock.ts` reuses the `AzureWebJobsStorage` account for its lease blobs: it reads `AzureWebJobsStorage__accountName` (or `__blobServiceUri`) for the endpoint and `AzureWebJobsStorage__clientId` (falling back to `MANAGED_IDENTITY_CLIENT_ID`) for the UAMI it authenticates as (scope `https://storage.azure.com/.default`). It creates a `drain-locks` container on first use, so the UAMI needs **Storage Blob Data Contributor** (container create + blob lease) — already satisfied by the identity-based `AzureWebJobsStorage` setup, which requires Blob Data Owner/Contributor. Tunables (all optional, read once at load): `DRAIN_LOCK_ENABLED`, `DRAIN_LOCK_CONTAINER`, `DRAIN_LOCK_LEASE_SECONDS` (15–60), `DRAIN_LOCK_RENEW_MS`, `DRAIN_LOCK_ACQUIRE_WAIT_MS`, `DRAIN_LOCK_ACQUIRE_POLL_MS`.
- **Reprocess replays per-message, so a moved conversation = one ticket per email.** The Reprocess drain replays each message individually. Dragging an Outlook conversation moves every email, so with `TICKET_CREATE` on it creates as many ticket operations as messages; move one message to replay a thread once. Reprocess is always requester-silent. With `FOLLOWERS_NOTICES` on, each replayed append still fires an indistinguishable webhook, so followers/loop people are re-noticed per message (known admin-bounded limitation; possible escape hatch: a per-`(ticketId,eventID)` claim).

## Accessing logs (Application Insights)

> ⛔ **This working copy has no live connection.** Do **not** attempt `az monitor app-insights query`,
> `az functionapp …`, or any other live Azure/Helpdesk call from this environment — there is no
> network path or credential, so the calls only waste a turn. Diagnose from the source, the tests,
> and log excerpts the user pastes in. Everything below is reference material for someone working
> from a machine that *does* have access.

Runtime logs (the `createStepLogger` traces, host status, exceptions, request/dependency telemetry) live in **Application Insights**, queried with `az monitor app-insights query`. Two environment gotchas bite every time:

- **Zscaler cert split.** The data-plane endpoint (`api.applicationinsights.io`) is TLS-intercepted by Zscaler, so `az monitor app-insights query` needs `REQUESTS_CA_BUNDLE` pointing at the Zscaler root (`%USERPROFILE%\Zscaler Root.cer`, the same file as the npm `cafile` / `NODE_EXTRA_CA_CERTS`). But ARM calls (`az account`, `az resource list`, `az functionapp …`) **fail** if it's set — `unset` it for those. Empty-string counts as "set to an invalid path", so use `unset`, not `REQUESTS_CA_BUNDLE=`.
- **Output rendering.** Use `-o json` (table/tsv often render blank here) and parse it; aggregates aliased `last` error with `BadArgumentError` (reserved-ish) — name them something else.

**Environments (App ID is what `--app` wants for a data query — no subscription/RBAC needed once you have it):**

| Env | Subscription | Function app / RG | App Insights (App ID) |
|-----|--------------|-------------------|------------------------|
| **Dev** | `SUB-CORE-HELPDESK-SPK-DEVT000` (`95ed3ea8-d8bc-452c-8ea1-8b2ef682219d`) | `funcapp-core-helpdesk-dev000` / `rg-core-func-spk-helpdesk-dev000` | `fb576bae-2a09-465f-9130-56a8ac1bbe64` (component `aicorehelpdeskprod000`) — **verified** |
| **Prod** | `SUB-CORE-HELPDESK-SPK-PROD000` (`da39198a-32a8-469a-917a-c7eb9ea347d4`) | `funcapp-core-helpdesk-prod000` / `rg-core-func-spk-helpdesk-prod000` | `fb576bae-2a09-465f-9130-56a8ac1bbe64` — **same component as Dev** (confirmed 2026-08-05 from prod's `APPLICATIONINSIGHTS_CONNECTION_STRING`) |

> ⚠️ **Both environments share ONE App Insights component** (`aicorehelpdeskprod000`, App ID `fb576bae…`) — confirmed 2026-08-05 by reading `funcapp-core-helpdesk-prod000`'s `APPLICATIONINSIGHTS_CONNECTION_STRING` (same `ApplicationId` as Dev's). Every query must split environments with `| where cloud_RoleName == 'funcapp-core-helpdesk-<env>000'` or it silently mixes prod and dev telemetry. (The 2026-06 observation that 30 days of the component held only dev telemetry is consistent: prod's legacy mail-flow switch was off, so its handlers returned immediately and emitted almost nothing.)

**Query pattern** (PowerShell; bash is the same with `export`/`unset`):

```powershell
$env:REQUESTS_CA_BUNDLE = "$env:USERPROFILE\Zscaler Root.cer"   # set for data queries; Remove-Item env:\ for ARM
$App = "fb576bae-2a09-465f-9130-56a8ac1bbe64"                    # dev
az monitor app-insights query --app $App -o json --analytics-query `
  "traces | where timestamp > ago(1d) | where severityLevel >= 3 | project timestamp, message | order by timestamp desc | take 50"
```

Handy queries (the `--analytics-query` body): error-severity traces `traces | where severityLevel >= 3`; Helpdesk bounce-block `union traces,exceptions | where * has 'limitExceeded' or * has '409'`; drain-lock canonicalization failures `traces | where message has 'canonical'`; dead-lettered drains (the `mail-poison` ERROR logs) `traces | where severityLevel >= 3 and message has 'poison'`.

## Testing

Jest + ts-jest. Tests live beside the source as `src/functions/*.test.ts` and compile through **`tsconfig.test.json`** (CommonJS) — separate from the app build (`tsconfig.json`, NodeNext), which **excludes `*.test.ts`**.

Conventions:
- HTTP/Graph boundaries are mocked with `axios-mock-adapter` on the relevant axios instance. For `process-mail`/`helpdesk` handler tests, `axios.create` is spied (Helpdesk instance) and/or `./graph-mail` / `./sharepoint` are mocked at the module boundary.
- `@azure/identity` `getToken` is mocked for the SharePoint Graph pipeline tests (`sharepoint.e2e.test.ts`).
- `jest.config.js` strips the `.js` extension that `index.ts` puts on its relative imports (`moduleNameMapper`).
